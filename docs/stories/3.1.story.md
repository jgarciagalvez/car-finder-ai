# Story 3.1: Performance - Refactor VehicleCard State Management

## Status
Done

## Story
**As a** user,
**I want** the dashboard to remain stable when scrolling through all vehicles,
**so that** I can browse the entire vehicle list without crashes or performance degradation.

## Acceptance Criteria
1. Each VehicleCard only maintains essential local state:
   - `currentImageIndex` (for image carousel)
   - `imageError` (for broken image handling)
   - `isNotesExpanded` (for notes UI toggle)
   - `notes` (for notes textarea value)
2. Operation states (`isTranslating`, `isAnalyzing`, `isUpdatingStatus`, `isSavingNotes`) are moved to shared context/manager (e.g., track by vehicle ID in context)
3. Error and success messages (`actionError`, `actionSuccess`) are managed centrally instead of per-card
4. Dashboard loads ALL non-deleted vehicles from database on mount but renders them progressively:
   - API fetches entire dataset (no limit - works with 50, 500, or 5000+ vehicles)
   - Deleted vehicles (status='deleted') are excluded from initial fetch
   - Initial render: First 50 vehicles displayed
   - Scroll-based rendering: Additional vehicles rendered as user scrolls down
   - Sorting/filtering operates on complete dataset (all vehicles in memory)
   - Dashboard remains stable and responsive regardless of dataset size
5. Search/sort/filter bar (SearchAndFilters component) is sticky to the top of the viewport:
   - Bar remains visible when scrolling through vehicles
   - User can change sort/filter at any scroll position
   - Sticky behavior works across all viewport sizes (mobile/desktop)
6. When sort or filter changes, render count resets to 50 but scroll position is preserved:
   - User stays at current scroll position (no jarring scroll-to-top)
   - Only first 50 vehicles from NEW sorted/filtered list are rendered
   - User can manually scroll up to see newly sorted results
7. Personal notes remain visible and editable in dashboard cards with existing save/cancel button pattern
8. No regression in existing functionality (translate, analyze, status update, notes save/cancel)

### Architecture Context

#### Current State Management Problem [Source: Epic 3, Story 3.1 Context]

**Issue**: Dashboard crashes when scrolling past ~30-40 vehicles
**Root Cause**:
- Each VehicleCard maintains 10 React state variables:
  1. `currentImageIndex` - Image carousel position
  2. `isTranslating` - Translation operation loading state
  3. `isAnalyzing` - Analysis operation loading state
  4. `isUpdatingStatus` - Status update loading state
  5. `isSavingNotes` - Notes save loading state
  6. `notes` - Notes textarea controlled input
  7. `isNotesExpanded` - Notes expand/collapse UI toggle
  8. `actionError` - Error message for failed operations
  9. `actionSuccess` - Success message for completed operations
  10. `imageError` - Broken image fallback state

**Math**: 40 cards × 10 states = 400 state variables causing memory/performance issues

**Additional Issue - Sorting/Filtering Bug**:
- Current implementation: API fetches 50 vehicles at a time (pagination)
- Problem: Sorting/filtering only operates on loaded vehicles (not entire database)
- User expectation: Sort by price should sort ALL vehicles from database, not just loaded subset
- Root cause: `filteredVehicles` operates on `state.vehicles` which is paginated subset
- Example: User has 500 vehicles in DB, sorts by "Price Low to High"
  - Current (broken): Shows cheapest of loaded 50 vehicles
  - Expected (fixed): Shows cheapest of ALL 500 vehicles in database

**Solution Strategy**:

**Part 1: State Management Refactoring**
- **Keep local (4 states)**: Essential per-card UI state that doesn't need sharing
  - `currentImageIndex`: Carousel position (each card independent)
  - `imageError`: Image error state (per-card fallback)
  - `isNotesExpanded`: Notes UI toggle (per-card UI state)
  - `notes`: Controlled input value (needs local state for performance)

- **Move to context (6 states)**: Shared operation states and feedback messages
  - Operation states: `isTranslating`, `isAnalyzing`, `isUpdatingStatus`, `isSavingNotes` → Track by vehicle ID in context
  - Feedback messages: `actionError`, `actionSuccess` → Single global feedback state

**Expected Result**: 40 cards × 4 states = 160 state variables (60% reduction)

**Part 2: Progressive Rendering (Fixes Sorting/Filtering Bug)**
- **Load ALL vehicles on mount**: Change API call to fetch entire dataset (no pagination limit)
- **Store all in context**: `state.vehicles` contains ALL vehicles from database (regardless of count)
- **Sort/filter on full dataset**: `filteredVehicles` operates on complete array from database
- **Render progressively**: Only render first 50 VehicleCard components initially
- **Lazy render on scroll**: Increment `vehiclesToRender` by 50 when user scrolls near bottom
- **Performance maintained**: Only ~50-100 DOM nodes exist at any time (not thousands)

**Expected Result**:
- Sorting/filtering works correctly on ALL vehicles from database (50, 500, 5000+)
- Initial render: 50 cards × 4 states = 200 state variables
- Full scroll: 100 cards × 4 states = 400 state variables (but no performance issue due to refactored state)
- Memory footprint: ~2.5KB per Vehicle object (e.g., 500 vehicles = ~1.25MB) + minimal rendering overhead
- Scalability: Tested with full production dataset, not just sample size

#### Progressive Rendering Architecture [Source: apps/web/src/hooks/useVehicles.ts]

**Data Flow**:
```
API Call (on mount)
   ↓
state.vehicles = [ALL vehicles from database - no limit]
   ↓
filteredVehicles = sortVehicles(state.vehicles, sortBy).filter(statusFilter)
   ↓
visibleVehicles = filteredVehicles.slice(0, state.vehiclesToRender)
   ↓
VehicleDashboard renders visibleVehicles.map(v => <VehicleCard vehicle={v} />)
```

**API Request Pattern**:
```typescript
// Frontend calls:
const response = await fetchVehicles({ limit: 0 }); // or limit: 999999
// Returns ALL vehicles from database (status != 'deleted')

// Backend behavior:
const vehicles = await vehicleRepository.getAllVehicles(); // Fetches entire DB
const paginatedVehicles = vehicles.slice(offset, offset + (limit > 0 ? limit : vehicles.length));
// When limit=0, uses vehicles.length → returns ALL vehicles
```

**Implementation Pattern**:
```typescript
// In useVehicles hook
const filteredVehicles = useMemo(() => {
  const sorted = sortVehicles(state.vehicles, state.sortBy);
  if (state.statusFilter?.length > 0) {
    return sorted.filter(v => state.statusFilter!.includes(v.status));
  }
  return sorted;
}, [state.vehicles, state.sortBy, state.statusFilter]);

const visibleVehicles = useMemo(() => {
  return filteredVehicles.slice(0, state.vehiclesToRender);
}, [filteredVehicles, state.vehiclesToRender]);

const loadMoreForRendering = useCallback(() => {
  if (state.vehiclesToRender < filteredVehicles.length) {
    dispatch({ type: 'SET_VEHICLES_TO_RENDER', payload: state.vehiclesToRender + 50 });
  }
}, [state.vehiclesToRender, filteredVehicles.length]);
```

**Scroll Handler Pattern** (in VehicleDashboard):
```typescript
const handleScroll = (e: React.UIEvent<HTMLDivElement>) => {
  const { scrollTop, scrollHeight, clientHeight } = e.currentTarget;
  const isNearBottom = scrollHeight - scrollTop - clientHeight < 500;

  if (isNearBottom) {
    loadMoreForRendering(); // Render next 50 cards
  }
};

// In JSX
<div onScroll={handleScroll} className="overflow-auto">
  {visibleVehicles.map(vehicle => <VehicleCard key={vehicle.id} vehicle={vehicle} />)}
</div>
```

**Key Benefits**:
- Sorting/filtering operates on ALL vehicles (fixes bug)
- Only 50-100 DOM nodes exist at any time (performance maintained)
- Seamless UX (no "Load More" button needed)
- Single API call on mount (faster than pagination)

#### Performance Considerations [Source: architecture/frontend-architecture.md]

**React Re-render Optimization**:
- VehicleCard re-renders when parent passes new `vehicle` prop (from context updates)
- Context updates to `operationStates[vehicleId]` should only trigger re-render for that specific card
- Feedback message updates trigger re-render for all cards (acceptable - infrequent operation)
- Consider React.memo for VehicleCard if re-renders become excessive (future optimization)

**Memory Management**:
- Operation states should be cleaned up when vehicles are removed from list
- Add cleanup logic in reducer when `SET_VEHICLES` action occurs
- Feedback messages auto-clear after timeout (no memory leak risk)
- ALL Vehicle objects stored in memory (~2.5KB each):
  - Example: 500 vehicles = ~1.25MB memory footprint
  - Example: 1000 vehicles = ~2.5MB memory footprint
  - Modern browsers handle this easily (acceptable for local-first app)

**Progressive Rendering Performance**:
- Initial render: Only 50 VehicleCard components mounted
- Scroll rendering: Increments by 50 cards at a time
- Maximum DOM nodes: ~50-100 cards visible simultaneously
- Re-render on sort/filter: Resets to first 50 cards (scroll position PRESERVED - AC #6)
  - **Behavior Example**:
    ```
    User has 500 vehicles in database
    User scrolled to vehicle #100 (scroll position: 2000px)
    User clicks sort dropdown in sticky bar (no need to scroll up)
    User selects "Sort by Price (Low to High)"

    What happens:
    ✓ API: No new fetch (all 500 vehicles already in memory from initial load)
    ✓ Sort: filteredVehicles re-sorted (ALL 500 vehicles sorted by price)
    ✓ Render: vehiclesToRender resets to 50 (only first 50 cheapest rendered)
    ✓ Scroll: User STAYS at scroll position 2000px (NO auto-scroll to top)
    ✓ View: User sees vehicles #41-50 at bottom of viewport
    ✓ Action: User manually scrolls up to see vehicles #1-10 (cheapest in database)
    ✓ Result: TRUE cheapest vehicles shown, not cheapest of first 50 loaded
    ```
  - **Implementation**: Only dispatch `SET_VEHICLES_TO_RENDER` action, do NOT manipulate window.scrollTo()
  - Sticky bar enables sort/filter changes from any scroll position
- No virtualization library needed for current dataset size

**State Update Patterns**:
- Use functional updates for operation states to avoid race conditions
- Ensure feedback timeouts are cleared if component unmounts
- Keep notes as local state to avoid throttling textarea input performance
- Progressive rendering state updates trigger minimal re-renders (only VehicleDashboard)
